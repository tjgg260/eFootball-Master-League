## dribbling-skills

Dribbling/feints/skills spans three code layers plus one dt270 data pack. INPUT layer: match::pad::ThinkUnit{Dribble,Feint,KickFeint} (vf8 = the stick/command decoders) turn a raw pad direction into a dribble/feint intent, applying deadzones and angle-wrap. DECISION/STEERING layer: match::player::Action{Dribble,Feint,KickFeint} (ActionDribble vf20 0x1456220d0 is the main steering tick) choose target facing/turn and gate on ball state + speed. EXECUTION layer: match::anime::action::{Dribble,Feint,CarryBall,SeamlessDribble} play the actual motion, reading player attributes through the proven accessor 0x143ea8cb0 and combining them into motion parameters. The physical touch geometry (how far the ball is knocked, turn radii/speeds, close-control tightness) is DATA-DRIVEN from the dt270 ballplayer.o object (constant_player.bin, struct 75096 B): TurnData[1440] (per-input-angle turn touch lengths/angles/speeds), touch0[7] (per-touch-kind knock-on distance + frame count), and Feint{DataUse,disp_area,rate=0.9}. Skill-card gating everywhere goes through one bitfield test 0x1442c0000(player,skillId). CPU dribble-past aggressiveness comes from the already-mapped difficulty table row 26. The most moddable surface is therefore (a) the dt270 ballplayer tables — hex-editable in the CPK, no Denuvo issue, changes touch distance/close control/turn feel directly; (b) a handful of near-private .tls$ float cells in the steering/carry ticks (speed→turn-tolerance map, the 1.3x carry-speed multiplier); (c) the skill bitfield and attribute-id reads that gate which players get which behaviour.

## cpu-attacking-decisions

match::ai::ActionSelector* is the CPU's off-ball/on-ball attacking-intent scorer. A shared dispatcher match::ai::ActionSelectorScore::Score (vf2, 0x143df1080) loops over 11 (0xb) candidate teammate slots; for each it calls the subtype's virtuals — vf4 (0x20, candidate-mask generator), vf5 (0x28, score-float producer) and vf6 (0x30, target-position/weight) — writes a per-slot float score into an array at this+0xc, and keeps only slots whose score is strictly > 0 (comiss against 0). Selection/argmax then happens in ActionSelectorManager / match::ai::Judge, which pick the highest-scoring run/action and hand it to PlayerOffence. Each attacking pattern is its own subclass whose vf4/vf5 encode a distinct geometry model: ChanceSpaceRun, CounterSpaceRun, DiagonalRun, SecondLineSpaceRun, PostPlay, plus the non-Score selectors GoalGet (shoot), CenteringGet (cross) and Overlap. CRITICAL FINDING: the entire scoring surface is DETERMINISTIC — grep of every live method found NO calls to the LCG/Gaussian RNG (0x144345e00/0x144345eb0), the pct-roll (0x143eafd30), the CPU difficulty GetParam (0x1442e48f0)/level table (0x146c06f40), or ConstantManager (0x145348d70). CPU shoot/pass/run choice is a pure function of pitch geometry + a handful of player attributes; difficulty and randomness are injected downstream in EXECUTION, not here. The tunable surface is therefore hundreds of hard-coded float geometry constants (distances, squared-distance gates, angles in degrees, normalizer weights) baked into .tls$ float cells, plus a few attribute reads. Highest-impact levers are the shot-range gate (dist² vs 1444 = 38² in GoalGet), the cross-range gate (324 = 18² in CenteringGet), the kick_power read that weights shot desirability, and the per-pattern distance thresholds that decide when a run is even offered. Two selector types (LineBreak, PullAway) are INERT — their vf3/vf4/vf5 are xor/ret stubs that return 0, so they never contribute a candidate.

## shooting-behaviour

Shooting behaviour splits into three code stages, all in the plaintext .xcode section, all live. (1) DECISION/AIM — match::player::ActionShoot::vf6 0x1441b4f60 (808 ins): the CPU chooses the aim point on goal and the shot "power ratio". It seeds a base target from a per-action shot-context descriptor (goal-mouth geometry), then adds scatter with FIVE Gaussian draws (0x144345eb0) whose sigma = goalAngleFrac^2 + 0.8 + (6-cpuLevel)/6, i.e. wider aim error for weaker CPU and worse angles; the resulting aim writes ActionShoot+0x8f4 (target xyz), +0x8f8/+0x8fc (spread), +0xe74 (aim yaw), and a 0..1 shot-power ratio to +0xe7c (clamped [0,1]); shot STYLE is emitted as byte +0xffa (0=drive,1,2,3) and bitflag +0xffc\|=4 (finesse/lob). Style/power branch is chosen from a shot-context category (descriptor.+8) fetched from the static table at 0x1486bfbc0 (indexed by action id 0..0x15 via 0x1443395a0), plus CPU-level probability gate GetParam(row0x1e=30). (2) EXECUTION SPEED — 0x143eeed40: converts the charged gauge (power ratio) into km/h using dt270 shoot gage tables get(0x6d), interpolating table rows by the shot attribute id 0x2b fraction (attr-40)/59 and by 5 m distance-to-goal band, through a fixed quadratic gauge curve, plus a skill-7/attr-0x2b bonus. (3) LAUNCH ELEVATION — 0x143fdf0c0 reads dt270 shoot.normal_dy/control_dy. Entry points: ActionShoot vf2 0x14561fe20 (tick, calls setup helpers 0x145624f70/0x145625170), vf6 0x1441b4f60 (aim/power decision). The kick EXECUTION error (already mapped, 0x14401a900) is applied downstream and is out of scope. Tunable surface = the geometry/scatter float cells and the level→sigma curve in vf6, the shot-context descriptor table 0x1486bfbc0, the attribute→speed normalization (40f/59f) and gauge quadratic in 0x143eeed40, and the dt270 shoot object (gage tables, *_dy) in the CPK.

## difficulty-rows

The 44-row x 10-col CPU-level table B at 0x146c06f40 (active on PC, platform class 3) is read ONLY through AiLevelUnit::GetParam 0x1442e48f0 (idx 0..43) and its boolean wrapper AiLevelUnit::IsEnabled 0x1442e4c00 (\|GetParam\|>1.19e-7). I found all 44 consumer callsites by an exhaustive E8-rel32 scan of every executable section (44 direct calls, one of which is GetParam being invoked from inside IsEnabled), back-traced the idx each passes, and mapped every callsite to its containing method via RTTI. Result: every row is now named. Row stride 0x2c; byte0 = 'discrete' flag (1 = no half-step interpolation, used for the 0/1 IsEnabled flag rows); value(row,col) lives at 0x146c06f40 + row*0x2c + 4 + col*4. Column->level: c0 BEGINNER, c1 AMATEUR, c2 REGULAR, c3 PROFESSIONAL, c4 TOPPLAYER, c5 SUPERSTAR-minus, c6 SUPERSTAR, c7 LEGEND-minus, c8 LEGEND, c9 LEGEND-plus (the real in-game columns are 0-4,6,8). The table splits into four families: (a) reaction/delay frame counts that shrink with level (rows 0,3,23,24,25,26,43), (b) timing/rate/distance multipliers and probabilities (rows 1,2,11,12,14,15,17,18,27,28,29,30), (c) 0/1 ability-gate flags read through IsEnabled (rows 4-10,13,16,19,20,21,22,32,33,39,40,41,42), and (d) SIX rows with no consumer anywhere in the exe -> dead in this build (rows 31,34,35,36,37,38). Consumers cluster in match::ai::ActionSelectorGoalGet::vf2 (the CPU attacking-decision evaluator: rows 3,5,6,8,14,18), the bp think-units (ThinkUnitPassTarget rows 23-25/27-30/39-41, ThinkUnitShoot rows 32/33, ThinkUnitDribbleChallenge row 26, ThinkUnitSetPlay row 42), and the player Action* executors (ActionPress row2, ActionWaitTimer row0, ActionDelay rows13/15/16/17, ActionShoot row30, ActionMark row9, PassGetRouteBallFollow rows10-12) and command_service::CommandResponse (rows 19-22). Best single lever remains an in-memory (VirtualProtect) edit of the table: copy a lower-level column into c6/c8 to weaken SUPERSTAR/LEGEND, or hook GetParam for a global rescale. dt270 JSON carries no per-level tables (confirmed prior) so all difficulty tuning is here.

## passing-behaviour

Passing behaviour splits into a TARGET-SELECTION/BUILD stage (free functions in .text 0x143fde000-0x143ff1000 and the PassGet consumers near 0x14415f000) and a COMMIT/EXECUTE stage (the match::player::Action*Pass vtables, all bases match::ai::ActionBall, sharing kick executor ActionBall::vf2 = 0x14561fe20). The build stage pulls almost all of its numbers from five dt270 ConstantManager objects fetched through get() 0x145348d70 via the singleton at 0x148c22b98: get(0x68)=centering, get(0x69)=flypass, get(0x6a)=grounderpass, get(0x6c)=passget, get(0x6e)=throughpass. Their fields (names/offsets from tools/data/dt270_schema.json, live values from tools/gameplay_tune.py) ARE the primary modding surface — pass target search cone/radius, pass-speed tables, through-ball lead timing, assisted-aim snap windows, and receiver-run behaviour. On top of that sit a handful of hardcoded exe constants and one pivotal gate: the [player+0x362c]&1 "assist" flag that switches every pass builder between assisted-target snapping and manual aim. The Action*::vf6 methods only translate the chosen target into the kick-request struct (offsets +0xe74 dir, +0xe7c power, +0xe88 target-attr, +0xff9 pass-kind, +0xffa lob); the actual scoring lives upstream in the builders below. Kick EXECUTION error is out of scope (already mapped). Confidence: get()-index->object and the 0x362c gate were followed in code (proven); mapping individual dt270 fields to their exact in-function use is proven for the ones traced and likely (structure+name) for the rest.

## goalkeeper

The GK subsystem is entirely code-driven — dt270 has NO goalkeeper constant object (schema has 36 types, none GK/catch/deflect/dive/save related), so every lever is an exe float/int constant or an attribute read, not a CPK-editable field. ## attribute-model

The per-player MATCH ability array is a flat byte array at matchPlayer+0x394, indexed directly by attribute id (0..0x3c). Read path (all proven): 0x143ea8cb0(player,id) reads playerIdx byte [player+0x2bd8] and env [player+0x47c0], calls 0x1442dd650(env,playerIdx,id) -> 0x1442d6ef0(env,playerIdx) resolves the match player from global table [0x1486bd888]+playerIdx*0x58+0x55a8 -> 0x144301840 returns base=player+0x394 -> 0x1441172b0(base,id) does `movzx eax, byte[base+id]`. The accessor returns the RAW byte; there is NO multiplicative scaler anywhere in the read path. Normalization to 0..1 is done per-consumer using two range tables via 0x1442bfae0(&loOut,&hiOut,id) [table A @0x146c00860, main attrs [40,99]] and its sibling 0x1442bfb10 [table B @0x146c008e0, main attrs [40,120]] — both live; consumers compute norm=(raw-lo)/(hi-lo). This range-table pair is the master normalization layer that underpins trap, weak-foot, and decision systems (but NOT the kick shot/pass piecewise 0x143ed71d0, which hardcodes its own 40/60/90 breakpoints). Weak-foot accuracy = id 0x27 (range [0,3], a 4-level value); stronger-foot = id 0x35 (range [0,1], boolean, compared to kicking foot [player+0x2bf6]). Skills & playstyles are NOT in this byte array: they live in a separate 73-bit bitfield at skillStruct+0xc0 (reader 0x1442c0000, id<0x49), the skillStruct fetched by 0x1442c3050 (stride 0x198, base +0xe8) / 0x1442e2640 / checker 0x143eadbe0. The human-readable attribute enum (offense_decision..star, then ps_* playstyles, s_* skills) is an inline string list at 0x1471d0558. Best global-scaler lever: shift the `lo` byte in range table A/B (0x146c00860/0x146c008e0) toward 0 to inflate every normalized attribute (or up to nerf); the single code choke-point for a multiplicative boost is a hook on 0x1441172b0/0x143ea8cb0. The roster(dt200)->match copy loop that fills +0x394 was not located (open question — whether it applies a condition/form multiplier).

## physical-locomotion

eFootball's locomotion is animation-driven: there is NO single "top-speed = f(Speed)" scalar. Instead, per-frame displacement = target_speed_kmh * 1000 / (fps * 3600), where fps comes from the platform framerate scale 0x14533ea80 and the km/h target is chosen per-tick by AI/pad think-units. Player attributes enter through one dominant global curve norm = clamp((attr-40)/80, 0, 1) (a second variant uses /(99-40)); Speed is match-ability id 0x16 and Agility (acceleration) is id 0x2a. The dt270 moveMatching object (ConstantManager index 0x6b) IS live: its RouteParameter[14] records (stride 0x38) supply acceleration/deceleration/rotation rate limits and motion-matching search weights; I proved consumers at 0x143ec8c8b/8eb4/9100/9562 read decMaxSpeedR(+0x1c) and accRateDif180(+8). Main entry points: km/h->frame converter 0x143c65890 (and inline copies), attribute reader 0x143ea8cb0(player,id)/raw 0x1442dd650(env,idx,id), AI move-speed think-unit 0x143f49c00, distance-tiered approach-speed picker 0x143f2c470, and the moveMatching consumer cluster 0x143ec8c00-0x143ec9700. ## rng-and-globals

THE match-simulation RNG is the LCG at 0x144345e00 (RandInt) — REFUTED-MT19937 was correctly refuted; a caller-bucket scan of all E8 calls in .xcode places the LCG family across the entire sim: 0x144345e00 (75 direct callers: match::ai::Judge/ActionSelectorScore/ZoneDefenceManager, match::ai::bp::* ImageUnit*/ThinkUnit*, match::player::ActionShoot, match::RandomControl, match::registry::RandomInfoRef, match::Injury, match::Player), its %100<pct wrapper 0x143eafd30 (77 callers, all match::anime::action::*), and the player wrapper 0x143ea9260 (218 callers, all match::anime::action::* / coach). The LCG is: state=(0x4513 - state*0x2d22b2e3)&0x7fffffff; result=int(state * 4.65661e-10f * max). It is a 4-SLOT generator: a per-context int32[4] state array with a per-slot modulus table at 0x146c34f20 = {100,5000,32768,32768}; slot 3 uses a distinct Lehmer form (state*0x15+7)%max. Slot 2 (mod 32768) is the universal match slot used by both player wrappers (state @ player+0x3bb4) and by match::RandomControl / match::registry::RandomInfoRef (state @ this+8). The Gaussian 0x144345eb0 (Box-Muller, 21 callers = kick error + ActionShoot aim) draws from the SAME LCG state — it is not a separate RNG, just a consumer, so it is per-subsystem layered on the one match RNG. SEED SOURCE: the LCG multiplier 0x2d22b2e3 occurs at ONLY 6 sites, all inside the RNG cluster 0x144345d90..0x1443461ae — there is no inlined clock/tick seeder anywhere in .xcode, and the player state array player+0x3bb4 has NO disp32 initializer other than the two reader wrappers, so it is zero-initialised at player construction. A zero state makes the first RandInt draw deterministic (=0x4513-based); combined with no reseed this means the match sim is fully deterministic given identical event ordering — which is exactly what the replay/observer/online-sync system needs (the shared match RNG state is checkpointed into the match registry under key "RANDOM" = URandomInfo, 0x58 bytes, via match::registry::RandomInfoRef @0x143c6a770). GLOBAL TUNABLES: the platform-tuning cluster at 0x148c22ab4..0x148c22ac0 is seeded from two int32 source constants 0x1482578f0(=54) and 0x1482578f4(=3): platform-class 0x148c22ab8=3 (selects CPU level table A/B + drives AI tick), AI-tick 0x148c22ac0=54, frame-rate float 0x148c22abc=54.0, companion 0x148c22ab4=3. UNMAPPED ConstantManager objects now traced: rating(0x51)=post-match player rating scoring (consumer match::record::ObserverUniqueMotion, 3 sites), modeMatchup(0x50)=AI/restart matchup coefficients (consumers match::ai::Judge reads a float table at obj+0xa4 indexed by (state)%6, match::Injury reads obj+8 bool, match::Player) and kickoff/restart positioning tables, cameraInplay(0x4e)=in-play camera geometry (Fov/Pan/PosY/PosZ/distance/height) — camera only, not behaviour.

## defending-tackle-foul

TACKLING, FOULS, REFEREE, CARDS in eFootball.exe. The referee classes (match::referee::Referee/Chief/Linesman, vftables 0x146bfe830/0x146bfeeb8/0x146bff548) are PASSIVE: their distinguishing methods (Chief vf21 0x1442bbde0, vf22 0x1442bb500, vf27 0x1442ba340; Linesman vf12/21/22/27) are pure referee-POSITIONING AI — jump tables on the match-state env fields ([env+0x3308] play state, [env+0x3304], [env+0x34a0] restart sub-type, [env+0x34c0]) that compute the ref's move target (this+0x910/+0x918) from per-restart geometry (5f/10f/4f offsets).
